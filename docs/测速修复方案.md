# 代理页测速（UrlTest）修复方案

> 对应问题：**测速后一段时间内只能测速一次，且测出来的结果不准。**

## 一、问题回顾

### 问题 1：一段时间内只能测速一次

测速链路：`ProxyActivity` → `Clash.healthCheck(group)` → Go `tunnel.HealthCheck(name)` →
对分组的每个 provider 调 `provider.HealthCheck()`（mihomo 子模块内）。

mihomo 的 `HealthCheck.check()`（`adapter/provider/healthcheck.go:128`）整体包在
`singledo.NewSingle(time.Second)` 里，语义是：

| 场景 | 行为 |
| --- | --- |
| 有测速正在进行 | 后来的调用**等待并共享同一次结果**，不发起任何新测试 |
| 测速结束不足 1 秒 | 直接返回缓存结果，同样不执行 |

而一次测速本身耗时很长：它会把该 provider 注册过的**所有测试 URL × 所有节点**测一遍
（errgroup 并发上限 10，单节点超时 5 秒，死节点吃满超时），订阅节点多时轻松跑几十秒。
期间无论怎么点"测速"（包括切到共享同一订阅的其他分组去点），都只是在搭便车等第一轮跑完。

另外：分组若走 `use:` 订阅 provider 且订阅未配置 `health-check.url`，`hc.url` 为空，
`execute` 对空 URL 直接跳过——点测速**什么都不测**，瞬间"完成"。

### 问题 2：结果不准

`core/src/main/golang/native/tunnel/proxies.go:186-192` 展示延迟时：

```go
testURL := "https://www.gstatic.com/generate_204"
for k := range p.ExtraDelayHistories() { // Go map 遍历顺序随机
    if len(k) > 0 {
        testURL = k
        break
    }
}
Delay: int(p.LastDelayForTestUrl(testURL)),
```

mihomo 的延迟历史按测试 URL 分开记录。节点同时属于多个分组时（如某个 url-test 分组
定时测 + 手动测速），历史 map 里有多个 URL 的条目，上面代码**随机挑一个**，导致：

- 显示的可能不是刚测的 URL 的结果，而是其他分组定时任务几分钟前的旧值；
- 随机挑中的 URL 最近一次失败时返回 65535，UI 显示空白（刚测成功的节点看起来"超时"）；
- 同一批数据两次刷新显示不同数值；"按延迟排序"也随之错乱。

此问题由 commit `dccab90`（"fix: delay"）引入。

## 二、修复方案

原则：**只改本仓库的 Go 胶水层，不动 mihomo 子模块**，方便后续升级子模块。

### 改动 1：绕过 singleflight，每次点击都真正测速（connectivity.go）

`core/src/main/golang/native/tunnel/connectivity.go` 重写 `HealthCheck`：

- 不再调用 `provider.HealthCheck()`，改为直接遍历 `g.Proxies()`，逐节点调
  `p.URLTest(ctx, url, nil)`；
- 用 `errgroup` + `SetLimit` 控制并发（建议 32，比 mihomo 的 10 快），
  整体加一个总超时（建议 15s），单节点沿用 5s 超时；
- 测试 URL 确定规则（与显示侧保持一致，见改动 2）：
  1. 分组 provider 的 `HealthCheckURL()`（订阅配置了 `health-check.url` 时）；
  2. 否则 `C.DefaultTestURL`（`https://www.gstatic.com/generate_204`）。

这样每次点击都发起真实的新测量，"只能测一次"消失；订阅未配 health-check 的分组
也能正常测速（不再依赖 `hc.url` 是否为空）。

```go
func HealthCheck(name string) {
    p := tunnel.Proxies()[name]
    if p == nil { ... }

    g, ok := p.Adapter().(outboundgroup.ProxyGroup)
    if !ok { ... }

    testURL := resolveGroupTestURL(g) // provider HealthCheckURL() 或 C.DefaultTestURL
    proxies := g.Proxies()

    ctx, cancel := context.WithTimeout(context.Background(), 15*time.Second)
    defer cancel()

    eg := &errgroup.Group{}
    eg.SetLimit(32)
    for _, proxy := range proxies {
        eg.Go(func() error {
            pctx, pcancel := context.WithTimeout(ctx, 5*time.Second)
            defer pcancel()
            _, _ = proxy.URLTest(pctx, testURL, nil)
            return nil
        })
    }
    _ = eg.Wait()
}
```

注意：`URLTest` 的返回值和错误可忽略——mihomo 内部会把成功/失败与延迟写入
该 URL 的历史（`adapter/adapter.go:166`），显示侧据此读取。

### 改动 2：显示与测速使用同一个 URL（proxies.go）

`convertProxies` 删除"随机挑 URL"的逻辑，改为**传入确定的 testURL**：

- `QueryProxyGroup` 增加 `testURL string` 参数（或包级函数
  `resolveGroupTestURL(g)` 复用改动 1 的逻辑）；
- `Delay: int(p.LastDelayForTestUrl(testURL))`；
- `collectProviders`（当前未被调用）同步修正或直接删除，避免留坑。

显示语义明确化：`LastDelayForTestUrl` 失败返回 65535，Kotlin 侧
`ProxyViewState.update()` 中 `> Short.MAX_VALUE` 显示为空——保持"空白=超时/未测"
即可，无需改 UI。

### 改动 3（可选，体验优化）：测速期间分批刷新

现状是全部测完才刷一次界面（`ProxyActivity.kt:93-100` 测完才发 `Reload`）。
可选优化：

- 简单版：Go 侧 `HealthCheck` 每完成 1/3 节点回调一次 UI 刷新（bridge 已有
  completable 回调机制，扩展一个 progress 回调即可）；
- 不做也不影响正确性，一期可跳过。

### 不改的地方（说明）

- mihomo 子模块的 `singleDo`/healthcheck 不动——定时健康检查（lazy + interval）
  对后台任务来说是合理的节流，问题只在于手动测速复用了这条路径；
- `HealthCheckAll`（`connectivity.go:43`）当前仅在 `SuspendModule` 的不可达分支
  被调用，保持原样即可；若后续想恢复"息屏自动测速"，也应改走新的直测逻辑。

## 三、验证清单

1. 节点多 + 多数超时的订阅：连点"测速"，每次都应有新结果（观察日志
   `Health Checking, proxy: ...` 的 id 变化）；
2. 同一节点属于 url-test 分组（定时测，URL A）和 selector 分组（手动测，URL B）：
   手动测速后显示的数值应来自 URL B，且两次刷新数值一致；
3. 按延迟排序：超时（65535）节点稳定排在末尾；
4. 未配置 `health-check.url` 的 `use:` 分组：点测速有真实请求发出（抓包或看日志）；
5. 回归：切换节点、分组刷新、重启核心后测速仍正常。
